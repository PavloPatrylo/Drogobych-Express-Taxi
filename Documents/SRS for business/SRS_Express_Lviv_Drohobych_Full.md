## 1. Вступ

### 1.1 Призначення

Даний документ є специфікацією вимог до програмного забезпечення (SRS) для автоматизованої омніканальної системи бронювання «Експрес Львів–Дрогобич». Документ призначений для:

- Команди розробників, які здійснюватимуть реалізацію системи
- Архітекторів програмного забезпечення, відповідальних за проєктування архітектури
- Тестувальників, які здійснюватимуть перевірку відповідності реалізації вимогам
- Менеджерів проєкту для планування робіт
- Замовників та стейкхолдерів для узгодження функціональності системи

Документ визначає функціональні та нефункціональні вимоги до системи, описує взаємодію між компонентами та визначає критерії прийняття готового продукту.

---

### 1.2 Область застосування

**Назва системи:** «Експрес Львів–Дрогобич»

**Опис системи:** Автоматизована омніканальна платформа, що замінює ручний облік пасажирів (паперові блокноти та телефонні дзвінки) для міжміських мікроавтобусних маршрутів. Ключова особливість — єдина централізована база даних (PostgreSQL) для замовлень з усіх каналів взаємодії: самостійне бронювання пасажиром через Telegram Bot, бронювання диспетчером за телефонним дзвінком, та фіксація посадки водієм на маршруті.

**Цілі системи:**

- Замінити ручний облік централізованою базою даних
- Надати пасажирам самостійний доступ до бронювання через Telegram Bot
- Забезпечити водіям швидкий інструмент для управління посадкою без ручного введення даних
- Надати диспетчерам і власнику Web-панель для управління розкладом, транспортом та аналітикою
- Виключити можливість overoverbooking завдяки транзакційним блокуванням на рівні БД

**Межі системи:**

Система охоплює:
- Самостійне бронювання пасажирами через Telegram Bot
- Ручне бронювання диспетчером за телефонним дзвінком
- Управління посадкою водієм (стоячі пасажири, посилки, boarding validation)
- Генерацію та управління розкладом рейсів
- Управління автопарком та конфігурацією транспортних засобів
- Фінансову аналітику, аудит-слід та Trust Score для власника
- Систему ролей на основі булевих прапорців

Система **не** охоплює:
- Онлайн-платежі та еквайринг
- Юридичне оформлення транспортних документів
- Інтеграцію з державними реєстрами
- Мобільний застосунок (iOS / Android)
- Маркетплейс або рекламний модуль

**Вигоди від впровадження:**

- Виключення людського фактору при обліку місць
- Централізований журнал усіх бронювань з усіх каналів
- Можливість аналізувати завантаженість рейсів та надійність пасажирів
- Зменшення навантаження на диспетчерів
- Повний аудит-слід: хто, коли і звідки вніс кожне бронювання

## 2. Загальний опис

### 2.1 Перспектива продукту

Система «Експрес Львів–Дрогобич» є самостійним програмним продуктом, що функціонує за архітектурою omni-channel з єдиним Core API. Система складається з наступних основних компонентів:

**Telegram Bot UI (Client & Driver Layer):**
- Розробляється з використанням Python та бібліотеки aiogram 3.x
- Два режими роботи: пасажирський (для всіх зареєстрованих) та водійський (для `is_driver = true`)
- Інтерфейс на основі inline-клавіатур без ручного введення тексту для водія
- Не містить бізнес-логіки — виключно UI-прошарок поверх Core API

**Web Admin Panel (Management Layer):**
- Веб-інтерфейс для диспетчерів та власника
- Взаємодіє з Core API через REST-запити
- Забезпечує візуалізацію розкладу, CRM для пасажирів, управління автопарком

**Core API & Booking Engine (Service Layer):**
- Розробляється на базі FastAPI (Python)
- Центральний сервіс бізнес-логіки: валідація лімітів, транзакційні блокування, генерація розкладу
- Захист від Race Condition через `SELECT ... FOR UPDATE` в транзакціях PostgreSQL
- Повний аудит-слід усіх операцій

**База даних:**
- PostgreSQL 15 як основна СУБД
- Взаємодія через SQLAlchemy 2.0 з асинхронним драйвером asyncpg
- Версіонування схеми через Alembic

---

### 2.2 Функції продукту

**Управління бронюваннями:**
- Самостійне бронювання сидячих місць пасажиром через бот
- Ручне бронювання диспетчером за телефонним дзвінком
- Швидка фіксація стоячих пасажирів та посилок водієм в 1 клік
- Скасування бронювань пасажиром та диспетчером

**Управління рейсами:**
- Генерація розкладу на день/тиждень
- Зміна статусу рейсу (SCHEDULED → BOARDING → ACTIVE → COMPLETED → CLOSED)
- Фінансове закриття рейсу після звірки каси

**Управління автопарком:**
- Додавання та редагування транспортних засобів
- Snapshot-копіювання лімітів місць при створенні рейсу

**Аналітика та безпека:**
- Trust Score та статистика надійності пасажирів
- Блокування ненадійних пасажирів
- Повний аудит-слід: хто і коли створив або підтвердив кожне бронювання
- Маркування джерела бронювання (BOT / WEB / PHONE / INSTAGRAM / DRIVER)

### 2.3 Характеристики користувачів

> **Важливо:** Ролі реалізовані через булеві прапорці (`is_driver`, `is_admin`, `is_superuser`) у таблиці `USERS`. Одна фізична особа може поєднувати кілька ролей одночасно.

#### 2.3.1 Пасажир (Passenger)

**Технічна експертиза:** Базовий рівень — вміє користуватися Telegram  
**Основні цілі:** Знайти зручний рейс та забронювати місце самостійно без дзвінка диспетчеру  
**Ідентифікація:** Telegram ID + номер телефону (через шеринг контакту)  
**Прапорці:** `is_driver = false`, `is_admin = false`, `is_superuser = false`

Функції:
- Реєстрація через шеринг контакту Telegram
- Пошук рейсів на обрану дату та напрямок
- Бронювання сидячого місця з перевіркою наявності
- Перегляд активних квитків та історії поїздок
- Скасування власного бронювання

Обмеження:
- Не має доступу до даних інших пасажирів
- Не може змінювати статус рейсу
- Заблокований пасажир (`is_active = false`) не може бронювати

#### 2.3.2 Водій (Driver)

**Технічна експертиза:** Базовий рівень — звик до швидких дій під час руху  
**Основні цілі:** Швидко керувати посадкою без відволікання від дороги  
**Прапорці:** `is_driver = true`

Функції:
- Перегляд маніфесту свого поточного рейсу
- Зміна статусу рейсу (BOARDING → ACTIVE → COMPLETED)
- Додавання стоячого пасажира в 1 клік (без введення імені/телефону)
- Запис посилки з опціональним коментарем
- Підтвердження посадки заброньованого пасажира

Обмеження:
- Не вводить імена чи номери телефонів під час руху
- Не має доступу до адмін-панелі
- Не може перевести рейс у CLOSED або CANCELLED

#### 2.3.3 Диспетчер (Admin)

**Технічна експертиза:** Середній рівень — досвід роботи з веб-формами  
**Основні цілі:** Приймати замовлення по телефону та вести облік рейсів  
**Прапорці:** `is_admin = true`

Функції:
- Генерація розкладу на день/тиждень
- Ручне створення бронювань за телефонними дзвінками клієнтів
- Скасування рейсів та бронювань
- Вирішення конфліктних ситуацій
- Фінансове закриття рейсів (статус CLOSED)

Характеристики:
- Кожне ручне бронювання фіксується з `created_by_id = dispatcher.id` (аудит)
- Може створювати тіньові профілі для клієнтів без Telegram

#### 2.3.4 Власник / Супер-Адмін (Owner)

**Технічна експертиза:** Середній-високий рівень  
**Основні цілі:** Контролювати бізнес, бачити «касу», управляти персоналом і автопарком  
**Прапорці:** `is_superuser = true`

Функції:
- Повний доступ до всього функціоналу диспетчера
- Перегляд фінансової статистики та audit trails
- Управління автопарком (додавання та редагування VEHICLES)
- Призначення ролей співробітникам (is_driver, is_admin)
- Перегляд Trust Score пасажирів та управління блокуваннями

### 2.4 Обмеження

#### 2.4.1 Технологічні обмеження
- Backend розробляється виключно на Python (FastAPI)
- База даних: PostgreSQL 15+; заміна на інші СУБД не передбачена
- Telegram Bot: виключно aiogram 3.x з async-підходом
- ORM: SQLAlchemy 2.0 + asyncpg; синхронний доступ до БД заборонений

#### 2.4.2 Бізнес-обмеження
- Один рейс може мати лише одного водія та один транспортний засіб
- Посилки (PARCEL) не займають місць у салоні (`passengers_count = 0`)
- Поле `created_by_id` у BOOKINGS обов'язкове і не може бути NULL
- Зміна конфігурації авто не впливає на вже створені рейси (Snapshot-принцип)

#### 2.4.3 Нормативні обмеження
- Паролі адміністраторів зберігаються лише у хешованому вигляді (bcrypt або argon2)
- Персональні дані пасажирів обробляються відповідно до законодавства України
- Доступ до фінансових даних обмежений виключно для `is_superuser = true`

#### 2.4.4 Організаційні обмеження
- Розробка ведеться у рамках визначеного бюджету та часових рамок MVP
- Усі зовнішні зміни вимог фіксуються у вигляді оновлень цього документа

### 2.5 Припущення та залежності

#### 2.5.1 Припущення
- Пасажири мають встановлений Telegram на смартфоні
- Водії мають смартфон з доступом до Telegram під час рейсів
- Диспетчер має постійний доступ до веб-браузера на ПК
- Наявне стабільне інтернет-з'єднання на всіх точках використання
- Замовник надає актуальний розклад рейсів та дані автопарку для початкового наповнення

#### 2.5.2 Залежності

Технологічні залежності:
- Доступність серверів PostgreSQL
- Доступність Telegram Bot API (api.telegram.org)
- Стабільність asyncpg та SQLAlchemy 2.0 для async-операцій

Зовнішні залежності:
- Telegram Bot API — для відправки повідомлень та отримання webhook-подій
- SMTP-сервіс або аналог — для адмін-нотифікацій (опціонально)

Правові залежності:
- Дотримання умов використання Telegram Bot API
- Відповідність вимогам щодо збереження персональних даних (телефони пасажирів)

## 3. Специфічні вимоги

### 3.1 Функціональні вимоги

---

#### 3.1.1 Модуль Telegram Bot — Пасажир

---

##### UC-P1: Реєстрація (шеринг контакту Telegram)

**Пріоритет:** Критичний (Must Have)  
**Залежності:** Відсутні

**Опис:** Система повинна ідентифікувати пасажира через стандартний механізм шерингу контакту Telegram та зберегти його профіль у базі даних.

**Вхідні дані:**
- Telegram ID (отримується автоматично)
- Номер телефону (через шеринг контакту Telegram)

**Елементи інтерфейсу бота:**
- Привітальне повідомлення при `/start`
- Кнопка «Поділитися номером телефону» (Telegram `request_contact`)
- Повідомлення про успішну реєстрацію
- Головне меню пасажира

**Функціональність:**

- UC-P1.1: Відображення кнопки шерингу контакту при першому запуску або спробі бронювання без реєстрації
- UC-P1.2: Отримання `telegram_id` та `phone` від Telegram API після підтвердження
- UC-P1.3: Перевірка наявності запису у `USERS` з таким `phone` або `telegram_id`
- UC-P1.4: Якщо запис відсутній — Core API створює новий `USERS` та початковий `USER_STATS` (`trust_score_cached = 100`, `total_trips = 0`, `total_noshows = 0`)
- UC-P1.5: Якщо існує тіньовий профіль (створений диспетчером) — Core API оновлює запис, прив'язуючи `telegram_id`
- UC-P1.6: Перехід до головного меню пасажира після успішної реєстрації

**Критерії прийняття:**
- Реєстрація завершується менш ніж за 3 секунди
- Тіньовий профіль коректно об'єднується без дублювання записів
- Повторна реєстрація з тим самим телефоном не створює нового запису

##### UC-P2: Пошук рейсів на обрану дату

**Пріоритет:** Критичний (Must Have)  
**Залежності:** UC-P1

**Опис:** Система повинна дозволяти пасажиру знаходити доступні рейси за обраним напрямком та датою.

**Елементи інтерфейсу бота:**
- Кнопки вибору напрямку: «Львів → Дрогобич» / «Дрогобич → Львів»
- Inline-клавіатура вибору дати: «Сьогодні», «Завтра», та дати на 5 днів вперед
- Список карток рейсів: час відправлення, ціна, кількість вільних місць
- Кнопка «Назад» до головного меню

**Функціональність:**

- UC-P2.1: Відображення вибору напрямку після натискання «Знайти рейс»
- UC-P2.2: Відображення inline-клавіатури вибору дати після вибору напрямку
- UC-P2.3: Запит до Core API: фільтрація `TRIPS` за `from_location_id`, `to_location_id`, датою `departure_time`, статусом `SCHEDULED` або `BOARDING`
- UC-P2.4: Для кожного рейсу обчислення `seats_available = seats_limit_snapshot − SUM(passengers_count WHERE booking_type='SEATED' AND status IN ('RESERVED','PAID','BOARDED'))`

##### UC-P3: Бронювання сидячого місця

**Пріоритет:** Критичний (Must Have)  
**Залежності:** UC-P2

**Опис:** Система повинна дозволяти пасажиру забронювати сидяче місце на обраний рейс із захистом від overoverbooking при конкурентних запитах.

**Передумова:** Рейс має статус `SCHEDULED` або `BOARDING`; є принаймні 1 вільне сидяче місце за даними попереднього екрану

**Елементи інтерфейсу бота:**
- Картка підтвердження: маршрут, дата, час відправлення, ціна
- Кнопка «Забронювати»
- Кнопка «Назад»
- Повідомлення про успішне бронювання з деталями квитка
- Повідомлення про помилку (Race Condition або блокування)

**Функціональність:**

- UC-P3.1: Відображення деталей рейсу та кнопки підтвердження
- UC-P3.2: Після натискання «Забронювати» — Core API відкриває транзакцію БД
- UC-P3.3: Core API виконує `SELECT seats_limit_snapshot FROM trips WHERE id = :trip_id FOR UPDATE` — встановлює рядкове блокування
- UC-P3.4: Перевірка актуальної кількості вільних місць у межах транзакції: `seats_available = seats_limit_snapshot − SUM(passengers_count WHERE booking_type='SEATED' AND status IN ('RESERVED','PAID','BOARDED'))`
- UC-P3.5: Якщо `seats_available ≥ 1` — Core API створює запис `BOOKINGS`: `booking_type = 'SEATED'`, `source = 'BOT'`, `status = 'RESERVED'`, `created_by_id = passenger.id`, `passenger_id = passenger.id`, `passengers_count = 1`
- UC-P3.6: Commit транзакції; бот відправляє підтвердження з деталями квитка
- UC-P3.7: Якщо `seats_available = 0` після отримання блокування (Race Condition) — Rollback; бот повідомляє пасажира

**Критерії прийняття:**
- При одночасному бронюванні останнього місця двома пасажирами — лише один отримує підтвердження
- Час відповіді бота: ≤ 3 секунди
- Заблокований пасажир (`is_active = false`) отримує повідомлення про неможливість бронювання

**Функціональність:**

- UC-P4.1: Core API отримує всі `BOOKINGS` де `passenger_id = current_user.id`
- UC-P4.2: Розподіл на дві групи: **Активні** — статус `RESERVED`/`PAID`/`BOARDED` та `departure_time` у майбутньому; **Історія** — решта

**Критерії прийняття:**
- Список завантажується менш ніж за 2 секунди
- Квитки коректно розподіляються на активні та архівні
- Для вже відправлених рейсів кнопка «Скасувати» не відображається

##### UC-P5: Скасування свого бронювання

**Пріоритет:** Критичний (Must Have)  
**Залежності:** UC-P4

**Опис:** Система повинна дозволяти пасажиру скасувати власне бронювання до відправлення рейсу.

**Передумова:** Бронювання має статус `RESERVED` або `PAID`; `departure_time` рейсу у майбутньому

**Елементи інтерфейсу бота:**
- Запит підтвердження: «Скасувати бронювання на [маршрут, дата, час]?»
- Кнопки «Так, скасувати» та «Ні, повернутись»
- Підтвердження успішного скасування
- Повідомлення про неможливість скасування (якщо рейс вже відправився)

**Функціональність:**

- UC-P5.2: Core API перевіряє: статус бронювання `RESERVED`/`PAID` та `departure_time` рейсу у майбутньому

- UC-P5.6: Якщо пасажир натискає «Ні» — бот повертається до «Мої квитки» без змін

**Критерії прийняття:**
- Скасування застосовується миттєво
- Після скасування місце стає доступним для нового бронювання
- Неможливо скасувати бронювання рейсу, що вже відправився

- UC-D3.2: Якщо `standing_available ≥ 1`: Core API створює `BOOKINGS`: `booking_type = 'STANDING'`, `source = 'DRIVER'`, `status = 'BOARDED'`, `passenger_id = NULL`, `created_by_id = driver.id`, `passengers_count = 1`

**Критерії прийняття:**

##### UC-D5: Підтвердження посадки (Boarding Validation)

**Пріоритет:** Критичний (Must Have)  
**Залежності:** UC-D1

**Опис:** Система повинна дозволяти водієві відмітити факт фізичної посадки пасажира, що має попереднє бронювання.

**Передумова:** Рейс у статусі `BOARDING`; у маніфесті є пасажир зі статусом `RESERVED` або `PAID`

**Елементи інтерфейсу бота:**
- У маніфесті поруч з кожним незаборденим пасажиром — кнопка «✓ Підтвердити»

**Функціональність:**

- UC-D5.1: Core API оновлює запис `BOOKINGS`: `status = 'BOARDED'`, `validated_by_id = driver.id`, `validated_at = NOW()`
- UC-D5.2: Маніфест оновлюється — пасажир переміщається у групу «На борту»

**No-Show сценарій (автоматичний або диспетчерський):**
- UC-D5.3: Після переходу рейсу в `ACTIVE` або `COMPLETED` — всі бронювання зі статусом `RESERVED`/`PAID` автоматично переводяться в `NOSHOW`
- UC-D5.4: Core API збільшує `USER_STATS.total_noshows` та перераховує `trust_score_cached` для відповідних пасажирів

**Критерії прийняття:**
- Підтвердження посадки виконується в 1 клік
- `validated_by_id` та `validated_at` заповнюються коректно
- Пасажири, що не підтвердили посадку, автоматично отримують статус NOSHOW

- UC-A2.1: Диспетчер обирає рейс та вводить номер телефону клієнта
- UC-A2.2: Core API виконує пошук у `USERS` за `phone`
- UC-A2.3: Якщо знайдено — підтягує ім'я автоматично; якщо ні — диспетчер вводить ім'я і Core API створює тіньовий профіль (`telegram_id = NULL`)
- UC-A2.4: Core API виконує бронювання з транзакційним захистом: `booking_type = 'SEATED'`, `source = 'PHONE'`, `created_by_id = dispatcher.id`, `passenger_id = found_or_created_user.id`
- UC-A2.5: Система відображає підтвердження з усіма деталями та аудит-інформацією

**Критерії прийняття:**
- Бронювання завершується менш ніж за 5 секунд
- `created_by_id` завжди містить ID диспетчера — не пасажира
- При відсутності місць Core API повертає `SEATS_LIMIT_EXCEEDED` з пропозицією альтернативного рейсу

##### UC-A3: Фінансове закриття рейсу (статус CLOSED)

**Пріоритет:** Критичний (Must Have)  
**Залежності:** UC-D2 (рейс у статусі COMPLETED)

**Опис:** Система повинна дозволяти диспетчеру фінансово закрити завершений рейс після звірки каси з водієм.

**Передумова:** Рейс має статус `COMPLETED`

**Елементи інтерфейсу Web-панелі:**
- Картка рейсу з підсумком: кількість SEATED / STANDING / PARCEL, `SUM(amount_paid)`, список усіх бронювань
- Кнопка «Закрити рейс (фінансово)»
- Запит підтвердження (незворотна дія)
- Відображення результату закриття

**Функціональність:**

- UC-A3.1: Адміністратор переглядає підсумок рейсу та звіряє з водієм
- UC-A3.2: Core API змінює `TRIPS.status → CLOSED`
- UC-A3.3: Всі бронювання зі статусом `RESERVED` або `PAID` автоматично переводяться в `NOSHOW`
- UC-A3.4: Core API оновлює `USER_STATS` для відповідних пасажирів
- UC-A3.5: Кнопка «Закрити рейс» недоступна для рейсів з іншим статусом (не `COMPLETED`)

**Критерії прийняття:**
- Статус `CLOSED` є незворотним — повернення неможливе
- `USER_STATS.total_noshows` оновлюється після закриття
- Фінансовий підсумок відображається коректно до підтвердження

##### UC-A4: Перегляд Trust Score та блокування пасажирів

**Пріоритет:** Високий (Should Have)  
**Залежності:** UC-P1 (наявність профілів)

**Опис:** Система повинна надавати адміністратору інструменти для моніторингу надійності пасажирів та управління блокуваннями.

**Елементи інтерфейсу Web-панелі:**

- Картка пасажира з повною статистикою
- Кнопки «Заблокувати» та «Розблокувати»
- Поле для нотатки про блокування

**Функціональність:**

##### UC-A5: Управління автопарком

**Пріоритет:** Критичний (Must Have)  
**Залежності:** Відсутні

**Опис:** Система повинна дозволяти власнику додавати та редагувати транспортні засоби з коректним збереженням snapshot-лімітів при створенні рейсів.

**Елементи інтерфейсу Web-панелі:**
- Список транспортних засобів: номер, модель, сидячі/стоячі, статус
- Форма додавання ТЗ: `plate_number`, `model`, `total_seats`, `total_standing`
- Форма редагування існуючого ТЗ
- Попередження при деактивації ТЗ з майбутніми рейсами

**Функціональність:**

- UC-A5.1: Власник заповнює форму та Core API створює `VEHICLES` (`is_active = true`)
- UC-A5.2: ТЗ стає доступним для призначення на рейси
- UC-A5.3: Редагування `total_seats` або `total_standing` → Core API оновлює лише `VEHICLES`
- UC-A5.4: **Snapshot-принцип:** зміна `VEHICLES` НЕ змінює `seats_limit_snapshot` у вже створених `TRIPS` — це поле незмінне з моменту створення рейсу

**Критерії прийняття:**
- Новий ТЗ одразу доступний у формі створення рейсу
- Зміна `total_seats` існуючого ТЗ не впливає на минулі та майбутні рейси
- `seats_limit_snapshot` копіюється виключно при `INSERT` рейсу

## 4. Додатки

### 4.1 Додаток A: Use Case — Повні сценарії

#### UC-FULL-1: Повний цикл рейсу (Happy Path)

**Актори:** Власник, Диспетчер, Пасажири (×N), Водій

**Основний сценарій:**

1. Власник додає новий мікроавтобус у розділі «Автопарк» (`total_seats = 18`, `total_standing = 5`)
2. Диспетчер генерує розклад на тиждень — Core API копіює ліміти у `seats_limit_snapshot` та `standing_limit_snapshot` для кожного рейсу
3. Пасажир A реєструється через Telegram Bot (шеринг контакту)
4. Пасажир A знаходить рейс та бронює місце → `BOOKINGS` запис зі статусом `RESERVED`, `source = BOT`
5. Пасажир B телефонує диспетчеру → диспетчер вручну вносить бронювання → `source = PHONE`, `created_by_id = dispatcher.id`
6. Водій відкриває маніфест, бачить 2 заброньованих пасажири
7. Водій натискає «Розпочати посадку» → рейс переходить у `BOARDING`
8. Пасажир A сідає → водій натискає «✓ Підтвердити» → `status = BOARDED`, `validated_by_id = driver.id`
9. Пасажир C підсідає на проміжній зупинці → водій натискає «+ Стоячий» → новий `BOOKINGS` запис (`STANDING`, `DRIVER`, `BOARDED`)
10. Водій натискає «Вирушити» → `ACTIVE`; водій натискає «Завершити рейс» → `COMPLETED`
11. Пасажир B не з'явився → при закритті рейсу його бронювання → `NOSHOW`; `USER_STATS.total_noshows++`
12. Диспетчер звіряє касу з водієм → натискає «Закрити рейс» → `CLOSED`

---

#### UC-FULL-2: Race Condition — захист від подвійного продажу

**Сценарій:** Залишилось 1 місце. Пасажири X та Y одночасно натискають «Забронювати».

1. Обидва запити надходять до Core API майже одночасно (різниця < 100 мс)
2. Транзакція X першою отримує `SELECT ... FOR UPDATE` — встановлює блокування рядка TRIPS
3. Транзакція Y очікує зняття блокування
4. Транзакція X перевіряє `seats_available = 1` → створює бронювання → commit → блокування знімається
5. Транзакція Y отримує блокування → перевіряє `seats_available = 0` → rollback
6. Пасажир X отримує підтвердження бронювання
7. Пасажир Y отримує: «На жаль, останнє місце щойно зайняли. Спробуйте інший рейс»

**Результат:** Рівно одне бронювання створено; overoverbooking виключено.

### 4.5 Додаток E: Глосарій

| Термін | Визначення |
|--------|------------|
| Overoverbooking | Ситуація, де кількість підтверджених бронювань перевищує фізичну місткість транспортного засобу |
| Race Condition | Стан системи, при якому два або більше конкурентних запити одночасно претендують на одне місце; усувається через `SELECT ... FOR UPDATE` |
| Snapshot | Незмінна копія значення конфігурації авто (seats/standing limit), збережена у таблиці TRIPS у момент створення рейсу |
| Тіньовий профіль | Запис у `USERS` із `telegram_id = NULL`, створений диспетчером для клієнта, що телефонує і не має Telegram |
| Trust Score | Кешований рейтинг надійності пасажира (0–100): `100 − (no_shows / max(trips, 1)) × 100` |
| No-Show | Пасажир, що мав активне бронювання, але не з'явився на посадку до відправлення рейсу |
| Boarding Validation | Підтвердження водієм факту фізичної посадки пасажира: заповнення `validated_by_id` та `validated_at` у `BOOKINGS` |
| Маніфест рейсу | Список усіх активних бронювань конкретного рейсу, що відображається водієві для управління посадкою |
| Audit Trail | Повний журнал дій через обов'язкові поля `created_by_id` та `validated_by_id` у таблиці `BOOKINGS` |
| CLOSED | Фінальний незворотний статус рейсу після фінансової звірки диспетчера з водієм |
| Source | Канал, через який надійшло бронювання: `BOT` / `WEB` / `PHONE` / `INSTAGRAM` / `DRIVER` |
| Тіньовий профіль | Запис USERS без telegram_id, що автоматично об'єднується з реальним профілем при реєстрації |
